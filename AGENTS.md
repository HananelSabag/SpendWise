## 0. WHAT THIS IS
Personal-finance web app for Israeli users. A local desktop worker scrapes Israeli banks/credit-card
companies and pushes transactions to a server; the web app shows balances, calendar-month cash-flow,
and insights. ILS-only. Bilingual EN/HE (RTL). Two git repos:

- `C:\CodingProjects\SpendWise`  → this repo: `client/` (React web) + `server/` (Node/Express API) + `cloudflare-worker/` (scraper proxy). GitHub `HananelSabag/SpendWise`, trunk-based on `main`.
- `C:\CodingProjects\spendwise-agent` → separate repo: the scraper worker. See its own `AGENTS.md`.

## 3. DOMAIN MODEL  (⚠ current model — supersedes older "billing_cycle_day" notes)
- **Bank account ≠ credit-card company.** Source of truth = `server/config/institutions.js` (14 sources; `kind` = `bank` | `credit_card`). Banks: yahav, hapoalim, leumi, mizrahi, discount, mercantile, otsar_hahayal, beinleumi, massad, pagi. Cards: isracard, amex, visa_cal, max. **A credit_card NEVER has a balance** — only charges (enforced at ingest, dashboard, hero). Client + agent keep mirror registries.
- **CALENDAR-MONTH accounting** (migrations 21/22): the old per-user `billing_cycle_day` field was **DROPPED** (mig 22). Attribution to an "economic month" now uses `salary_signatures` + `transaction_month_overrides`, computed in `services/monthlyAccountingService.js` / `calendarMonthSummaryService.js` (period helpers in `utils/calendarPeriod.js`, availability in `utils/calendarPeriodAvailability.js`).
- **Headline period totals = BANK cash-flow + manual**: `source_kind <> 'credit_card'`. The monthly card bill is one bank outflow (counted once); itemized card purchases are breakdown/detail only, never added on top. Real reference numbers (Hananel, user 1): income 13,328 / expenses 14,064 / net −736 for a clean cycle.
- **`ledger_class`** (txn col, mig 23) = derived economic class (`services/financialClassificationService.js`); nullable until trustworthy. Loan disbursements + own securities/investment transfers must NOT count as income (classification handles this).
- **Salary identity**: `salary_signatures` (user-confirmed) has `month_offset` (−2..0) → salary paid early/late is attributed to the correct work month. `services/salaryReviewService.js` proposes/reviews.
- **Card reconciliation**: a bank "settlement" row links to its card via `settlement_card_source` / `settlement_card_account` (`services/cardReconciliationService.js`, `monthlyAccountingService.js`). Brand matching is by **account last-digits + amount/date**, NOT Hebrew brand text (brand text is ambiguous: "לאומי ויזה" = a Max card; "כרטיסי אשראי" = Cal).
- **Pending FX** (mig 25): foreign pending card auths carry a temporary ILS estimate — `amount_is_estimated`, `fx_rate_used/source/as_of`, plus `original_amount/original_currency/charged_currency`. `services/bankPendingDedupService.js` handles pending→settled dedup.
- **Installments** (mig 23): `txn_kind`, `installment_number`, `installment_total`.
- **Soft delete**: bank rows delete as **tombstones** (`transactions.deleted_at`); dedup includes tombstones so nothing resurrects. Manual rows hard-delete. Unique key: partial `(user_id, bank_sync_id)`.
- **Merchant watch** (`merchant_watch_rules`, mig 24; `services/merchantWatchService.js`): user rules to flag/notify on merchant + amount condition (all/above/exact).

## 7. THE AGENT + SYNC SCHEDULING  (see `spendwise-agent/AGENTS.md` for internals)
- **Scheduling = "enqueue-on-claim"**: the agent polls `POST /bank-agent/jobs/claim` (~every 30 min); that poll IS the scheduler tick — `services/syncSchedulingService.js` enqueues due jobs (07:00/18:00 Asia/Jerusalem) at claim time. In-process node-cron never fires on the sleeping Render dyno. Verified in prod (trigger='schedule' jobs complete).
- **Claim scope + failover** (`services/agentClaimScope.js`, migration 39): a paired device claims only its own user; the shared Default Host claims users with no active device, PLUS users whose device has been silent >3h **but only for connections whose `bank_connections.credentials_sealed_to = 'default-host'`** (the shared host already holds a readable envelope, so this exposes nothing new — a device-sealed connection is never claimed by it). `credentials_sealed_to` is an identity (`default-host` | `device:<id>`), written on every credential write, never key material.
- **Sync health is DERIVED, never read off `bank_connections.status`** (`services/bankConnectionHealth.js`): an unclaimed job expires as `transient`, which by design leaves status/`consecutive_failures`/`last_error` untouched — so a dead agent leaves every column looking healthy. `GET /bank-connections` returns `sync_health` (`ok|queued|syncing|waiting_for_agent|agent_offline|stalled|needs_credentials|paused|error`) per connection plus an `agent` block (paired/last_seen/stale). **Real incident (2026-07-22→08-11): user 1 paired a device, its worker died, and 20 days of syncs black-holed while the UI showed a permanent "syncing now" spinner.** Never reintroduce a UI that infers health from `status` or from `latest_job_status === 'pending'` alone.
- Pairing does NOT re-seal existing connections: after pairing, saved credentials stay sealed to the old key and the new agent reports "Decryption failed" → normalized to terminal `CREDENTIALS_KEY_MISMATCH` (`bankAgentFailureService`), which tells the user to re-enter that connection's details.
- **Manual "sync now" limits** (`routes/bankConnectionsRoutes.js`): 2/day + 3h gap **per connection**; **admins (Hananel) are exempt**. Agent has its own cooldown gate too (bypassed when RAW-debug on).
- Agent stores creds encrypted (tweetnacl sealed), pairs via `agent_devices`/`agent_pairing_codes`. `bank_processed_date` = provider `processedDate` verbatim.

## 11. SHARED GROCERY LIST  (migration 40 — replaced the old shopping wishlist)
One shared household supermarket list for two-plus people (Hananel + Nofar), built to be used one-handed while walking a shop. Schema is in §4; these are the invariants that are easy to break.

- **Authorization is list-based and symmetric.** Every check is "does `grocery_list_members` have a row for (list, user)". The owner has a member row too. Item authorship (`added_by`/`purchased_by`) is history, never permission. All of it lives in `middleware/groceryAccess.js` — do not write a second, slightly-different rule anywhere else.
- **The active trip IS the list.** `grocery_trips` has exactly one `status='active'` row per list (partial unique index). "Finish shopping" archives it, opens a fresh one, and **carries unpurchased leftovers forward**. Purchased items are never deleted to clear the UI — history is backed by real rows.
- **Category keys are language-neutral** (`produce`…`other`, in aisle order). The list lives in `server/services/groceryCategories.js`, mirrored in `client/src/components/features/grocery/groceryCategories.js` and in the migration's CHECK constraint — a test asserts the two lists match. Labels come from `translations/{en,he}/grocery.js`. **Never store a Hebrew label as a domain identifier again.**
- **Edit lease (single-writer).** `grocery_lists.lock_*` + a monotonic `version`. Acquire is ONE atomic UPDATE whose WHERE clause is the mutual exclusion (unlocked, or expired, or same user+session); TTL 60s with a 20s client heartbeat, released after ~45s idle or on leaving the screen. Taking/dropping the lease bumps `version`; heartbeats deliberately do not. An expired lease is swept lazily by `GET /grocery/state` (no cron). Contention answers **409 `GROCERY_LOCKED`** with the holder. Every mutation route goes through `requireLease`, which implicitly takes a *free* lease so ordinary tapping needs no "Edit" mode — a disabled button is never the protection.
- **CORS carries the lease headers.** `X-Grocery-Session` / `X-Grocery-Lease` make every list request preflighted, so both are in `allowedHeaders` in `index.js`, and `X-Grocery-Lease` is also in `exposedHeaders` because the client reads the token back off the response when the server grants a free lease. Adding another `X-*` header without updating both lists fails silently in the browser with status 0 and **no server log at all** — that is what a "the page hangs on its skeleton" report means here. Regression tests live in `__tests__/groceryAccess.test.js`.
- **Live updates = visibility-aware version polling**, not SSE — the Render dyno sleeps and long-lived connections are unreliable there. The client polls `GET /grocery/state?version=N` every 4s while the tab is visible; unchanged answers are a ~40-byte body. Mutations update the TanStack cache optimistically and roll back on failure.
- **Sharing is a link (migration 41).** The primary flow is one recipient-less invitation per list — `grocery_list_invitations.invitee_email IS NULL` — created on demand, copied, pasted into whatever chat you already use. It is a deliberate trade (anyone holding the link can join) bounded by: joining is still an explicit Accept, the link expires in 14 days, the owner can revoke it, and a partial unique index allows only ONE open link per list so revoking really revokes. Redeeming a link does **not** consume it. Addressed email invitations still exist for the stricter case and are unchanged. Email delivery is not part of the critical path at all — see the Resend gap below.
- **Invitation links never auto-accept.** `/grocery/invite/:token` is a read-only preview; joining is an explicit `POST .../accept`, which is one transaction (status flip + membership insert) and idempotent. Invitations address an **email**, so someone without an account can be invited: the row keeps `invitee_id = NULL` and registration (`GroceryInvitation.linkForNewUser`, called from both password and Google signup) claims it — still pending, still needing acceptance.
- **A user works on exactly one list.** Accepting while already a member of someone else's list is *refused* (`GROCERY_ALREADY_IN_ANOTHER_LIST`) rather than silently resolved; an untouched auto-created own list is archived instead.
- **Notifications go to the one bell.** Grocery notifications are NOT filtered out of `NotificationBell` — hiding them is what made invitations invisible in full SpendWise mode. Opening the panel no longer marks everything read; only tapping one marks that one, and responding to an invitation clears only that invitation's notification (`Notification.markReadByDataValue`).
- **SpendWise linkage is manual and one-shot.** A finished trip stores its total as shopping history; "Add to SpendWise" creates ONE manual expense on request, stamped on `grocery_trips.transaction_id` (unique index + `IS NULL` guard = idempotent), and invalidates the same caches as any manual transaction. **Never create it automatically** — bank/card sync imports the same supermarket charge and would double-count it.
- **Storage split:** item photos → public `grocery` bucket (a picture of a yogurt, re-read on every refresh). Receipts → **private** `receipts` bucket; the API returns a 5-minute signed URL and `receipt_path` never leaves the server. New uploads must never be base64 in Postgres (that was the old wishlist's design). Both buckets are capped at 20MB with no MIME restriction; the server filter is the real gate.
- **Photos are compressed in the browser before upload** (`client/src/utils/imageCompression.js`). A phone camera file is 10–20MB and none of that survives a 40px thumbnail, so item photos are scaled to 1400px/~500KB and receipts to 2400px/~1.5MB (receipts keep more detail — small print). EXIF orientation is applied, WebP is used when the browser can encode it, and the quality steps down until it fits. Every failure path returns the original file untouched, including a **decode timeout** — some browsers silently drop a format and fire neither `load` nor `error`, which would leave the upload spinner running forever. The server's 20MB cap is therefore a safety net, not the working limit.
- **App mode is one resolver:** `client/src/utils/appMode.js`. `preferences.default_home` is the saved account default; a sessionStorage override is a one-time per-tab switch that never touches it. Grocery mode gets its own shell (`GroceryModeHeader` on desktop, `GroceryModeNav` on mobile), both of which always offer a way back to full SpendWise; full mode reaches the list from the menu sheet and Profile. `shopping_list_as_default_page` is still written for compatibility — drop it only after checking persisted user preferences.

**KNOWN CONFIG GAP — email invitations do not deliver.** `FROM_EMAIL=onboarding@resend.dev` is Resend's shared sandbox sender, and the Resend account has **zero verified domains** (checked 2026-09-04 via `GET https://api.resend.com/domains` → `data: []`). That sender can only deliver to the Resend account owner's own address, which is why verification mail to Hananel works and an invite to anyone else silently fails. Fix = verify a domain in Resend and point `FROM_EMAIL` at it; no code change helps. Until then the invite flow is deliberately email-independent: the owner always gets a copyable invite link and is told honestly whether the email went out.
